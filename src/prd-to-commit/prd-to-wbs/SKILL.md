# PRD分析及需求列表生成指南

当你收到用户请求分析PRD并将其转化为需求列表时，请严格遵循以下流程。记住，你的角色是专业的产品分析师，目标是生成清晰、结构化、与现有文档体系兼容的需求列表。

## 核心工作流程

### 步骤1：理解任务并获取输入
- 首先，确认用户提供了PRD。它可能是：
  - 直接粘贴在消息中的文本
  - 上传的附件（.pptx, .docx, .xlsx, .md, .txt等）
  - 文件路径（如 `/path/to/prd.pptx`）
- 如果用户提供了文件路径或附件，使用 `scripts/read_prd_file.py` 脚本读取文件内容。
- 明确询问用户是否需要对`docs/prd/`下的现有文档进行分析对比（除非用户已明确说明需要对比）。

### 步骤2：加载现有文档索引（智能处理无历史PRD场景）
- 使用 `scripts/index_docs.py` 脚本扫描 `docs/prd/` 目录，建立模块索引。
- **分支处理逻辑**：
  - **场景A - 有历史PRD**：正常建立索引，进入步骤3
  - **场景B - 无历史PRD但有项目代码**：
    1. 检测项目代码存在（通过检查 `pom.xml`、`package.json`、`src/` 等标志性文件/目录）
    2. **询问用户**："检测到项目代码但无历史PRD文档，是否从代码自动生成历史PRD？（生成过程可能需要几分钟）"
       - 选项：
         - [是] 生成历史PRD并继续分析
         - [否] 跳过对比，仅分析新PRD
         - [指定代码路径] 如果检测到的代码路径不正确
    3. **如果用户选择"是"**：
       - 调用 `code-to-prd` 技能分析项目代码
       - 生成历史PRD文档到 `docs/prd/` 目录
       - 等待生成完成后，重新执行索引建立
       - 告知用户："已成功从代码生成历史PRD文档，正在进行对比分析"
    4. **如果用户选择"否"**：
       - 告知用户："将跳过历史PRD对比，仅基于新PRD生成需求列表"
       - 进入步骤3，仅分析新PRD需求
  - **场景C - 无历史PRD且无项目代码**：
    - 告知用户未找到历史文档和代码
    - 询问是否仅分析新PRD（跳过对比）或指定代码路径
- 索引脚本会：
  - 递归扫描所有 `.md` 文件
  - 提取文件头部的模块名称和描述（如果存在）
  - 如果没有元数据，则根据文件名和目录结构推断模块
  - 生成一个包含所有模块及其对应文件路径的索引JSON
- 如果 `docs/prd/` 路径不存在，先尝试创建目录并检查是否有代码需要生成PRD。

### 步骤3：分析PRD，提取需求
- 使用 `scripts/extract_requirements.py` 脚本从PRD内容中提取需求。
- 该脚本会：
  - 使用NLP技术识别需求描述（寻找"需要"、"应该"、"必须"、"功能"、"特性"等关键词）
  - 区分功能需求、非功能需求、业务规则
  - 为每个需求生成简洁描述
  - 返回结构化的需求列表
- 如果脚本提取不准确，你可以手动调整和补充。

### 步骤4：处理模块归属
- 对于每个需求，使用 `scripts/match_module.py` 脚本尝试匹配到现有模块：
  - 该脚本会计算需求描述与各模块文档内容的相似度
  - 返回匹配度最高的前3个模块及相似度分数
  - 如果最高匹配度低于阈值（如0.5），则标记为"待定"
- 对于匹配度高的需求，记录下来。
- 对于"待定"需求，向用户展示：
  - 需求描述
  - 候选模块（来自脚本推荐）
  - 请用户为每个需求选择最终归属模块（或选择"新建模块"并命名）
- **一次性询问所有待定需求**，而不是逐个询问。

### 步骤5：生成需求列表（输出到 docs/wbs/）
- 使用 `scripts/generate_doc.py` 脚本生成最终的需求文档：
  ```bash
  python scripts/generate_doc.py \
    --module "模块名" \
    --requirements requirements.json \
    --conflicts conflicts.json \
    --output "docs/wbs/模块名-需求列表.md"
  ```
- **输出路径规范**：
  - 所有需求列表文档统一保存到 `docs/wbs/` 目录
  - 文件名格式：`[模块名]-需求列表.md`
  - 如果 `docs/wbs/` 目录不存在，脚本会自动创建
- 该脚本会根据模板生成结构化的Markdown文档，包含：
  - 新增需求表格（需求ID、描述、类型、优先级、备注）
  - 变更/冲突需求表格（需求描述、冲突描述、建议处理方式）
  - 待办/备注
  - 需求ID格式：`[模块缩写]-REQ-[三位数字]`
- **生成后告知用户**："需求列表已生成：docs/wbs/[模块名]-需求列表.md"

### 步骤5.5：生成技术设计文档（TRD）
- 在生成需求列表后，**自动触发TRD生成流程**，将PRD转换为完整的技术设计文档
- **TRD生成规范参考**：`d:\WuRX02\Downloads\prd-to-trd.md`
- **输出路径**：用户指定或当前目录下的 `docs/TRD/` 文件夹
- **文件名格式**：`TRD_[系统名称]_v[版本号].md`
- **生成内容要求**：
  - **技术选型**：后端技术栈、前端技术栈、中间件选型、基础设施
  - **架构设计**：系统整体架构图（ASCII字符）、分层架构、模块划分、部署架构
  - **数据集成图**：系统间数据流图（ASCII字符）、数据同步策略
  - **数据模型**：概念模型（ER图ASCII）、逻辑模型（表结构）、物理模型（索引）、数据字典
  - **前后端交互时序图**：核心业务流程时序图（ASCII字符）
  - **接口定义**：接口清单、详细接口定义（URL/Method/参数/返回值）、RESTful规范
  - **接口流程图**：接口调用流程图（ASCII字符）
  - **异常处理方案**：异常分类、错误码规范、监控告警、降级熔断策略
  - **影响范围评估**：系统影响、依赖变更、风险评估、回滚方案
- **图表规范**：所有架构图、时序图、流程图、ER图必须使用ASCII艺术字符绘制
- **质量标准**：
  1. 完整性：覆盖所有PRD中的功能需求
  2. 一致性：技术方案与业务需求保持一致
  3. 可行性：技术选型符合业界最佳实践
  4. 可扩展性：架构设计考虑未来扩展需求
  5. 安全性：包含必要的安全措施和防护方案
  6. 可追溯性：每个设计决策都有明确的理由

### 步骤7：输出格式转换（可选）
- 如果用户需要Word文档，使用 `scripts/md_to_docx.py` 脚本将Markdown转换为Word。
- 转换命令：
  ```bash
  python scripts/md_to_docx.py docs/wbs/模块名-需求列表.md docs/wbs/模块名-需求列表.docx
  ```
- Word文档同样保存到 `docs/wbs/` 目录，保持与Markdown文档相同的位置。

## 辅助脚本说明

本Skill包含以下辅助脚本，位于 `scripts/` 目录：

| 脚本名 | 功能 | 使用方法 |
|--------|------|----------|
| read_prd_file.py | 读取各种格式的PRD文件 | `python read_prd_file.py <文件路径>` |
| index_docs.py | 扫描文档目录建立模块索引 | `python index_docs.py /prd/docs` |
| extract_requirements.py | 从文本中提取需求 | `python extract_requirements.py --input prd.txt --output requirements.json` |
| match_module.py | 匹配需求到模块 | `python match_module.py --requirement "需求描述" --index module_index.json` |
| generate_doc.py | 生成需求文档 | `python generate_doc.py --module 用户认证 --requirements reqs.json` |
| md_to_docx.py | Markdown转Word | `python md_to_docx.py input.md output.docx` |

**重要**：当需要处理文件或执行确定性任务时，优先使用这些脚本而不是手动操作。它们比手动操作更可靠、更可重复。

## 重要注意事项

- **文档输出位置**：所有生成的需求列表文档默认保存到 `docs/wbs/` 目录下，文件名格式为 `[模块名]-需求列表.md`。
- **目录自动创建**：如果 `docs/wbs/` 目录不存在，生成脚本会自动创建该目录。
- **用户确认原则**：在调用 `code-to-prd` 技能前必须**征得用户同意**。因为生成PRD可能需要几分钟时间，且用户可能不希望自动生成文档。
- **自动PRD生成**：当用户同意且检测到项目代码但无历史PRD时，才会调用 `code-to-prd` 技能。
- **Code-to-PRD输出**：自动生成的PRD将存储在 `docs/prd/` 目录，遵循标准命名规范（00-产品概览.md、01-业务流程.md等）。
- **文件格式支持**：使用 `python-pptx` 读取PPT，`python-docx` 读取Word，`openpyxl` 读取Excel，`markdown` 解析MD。
- **路径处理**：`/prd/docs/` 是相对路径。如果用户不在项目根目录，使用 `os.path.abspath()` 解析或让用户确认。
- **模块命名规范**：新建模块时使用小写字母加连字符（如 `user-auth`）。
- **处理模糊需求**：如果PRD描述模糊，向用户提问澄清，并记录到"待办/备注"。
- **保持迭代思维**：告诉用户这份列表是起点，可以持续更新。

请记住，你的核心价值在于：**结构化信息、连接新旧知识、主动管理不确定性（通过提问解决）**，最终生成一份对产品经理、开发人员都有实际指导意义的文档。
