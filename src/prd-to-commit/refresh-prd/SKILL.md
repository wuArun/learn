# 刷新PRD - 更新产品需求文档

此技能用于基于现有代码库的变更，及时更新产品需求文档(PRD)，确保PRD文档的时效性和准确性。

## 核心能力

1. **变更识别**：自动识别代码库中的变更内容
   - 支持Git Diff方式：比较代码差异
   - 支持Git Log方式：基于提交记录
2. **文档同步**：将代码变更同步到PRD文档中
3. **版本管理**：维护PRD文档的版本控制
4. **一致性保证**：确保PRD与代码实现的一致性

## 刷新流程

### 第一阶段：变更分析

#### 1.1 代码变更扫描
- 识别最新代码变更（通过Git Diff、代码文件变更等）
- 分析变更类型（新增、修改、删除）
- 识别受影响的模块和功能

#### 1.2 影响范围评估
- 评估变更对业务流程的影响
- 识别涉及的实体、接口、角色和权限
- 分析数据模型变更

### 第二阶段：文档更新

#### 2.1 内容更新
- 更新受影响的业务流程文档
- 修改接口清单和数据字典
- 调整角色权限定义
- 更新错误码定义

#### 2.2 版本控制
- 为更新的文档添加版本号
- 记录更新内容和变更原因
- 更新文档修订历史

### 第三阶段：验证与输出

#### 3.1 内容验证
- 确保更新内容与代码实现一致
- 验证流程逻辑的正确性
- 核对数据模型的完整性

#### 3.2 输出文档
- 生成更新后的PRD文档
- 保持文档结构的完整性
- 提供更新说明文档

## 文档更新规范

### 更新范围
- **业务流程**：当流程逻辑发生变化时更新相应流程文档
- **接口规范**：API变更时更新接口清单和说明
  - **数据模型**：实体类变更时更新数据字典
    - **重要**：必须提取真实的 `@TableName` 表名
    - 禁止推断/虚构表名（如不要使用 `apqp_` 前缀）
    - 必须与代码中的 `@TableName` 值完全一致
  - **角色权限**：权限变更时更新角色权限矩阵
  - **错误码**：新增或修改错误码时更新错误码定义
  - **技术栈**：识别变更中使用的技术，特别是Rosefinch组件

### 更新原则
1. **完整性**：更新内容必须完整覆盖所有变更点
2. **准确性**：确保文档内容与代码实现完全一致
3. **一致性**：文档格式和术语使用保持一致
4. **可追溯性**：记录变更来源和变更说明
5. **真实性**：
   - 表名必须使用代码中 `@TableName` 注解的真实值
   - Rosefinch组件必须实际存在于代码import中
   - 禁止虚构任何服务类、注解或表名

## 文档命名与结构规范

### 文档存储位置
所有PRD文档统一存储在 `docs/prd/` 目录下：

```
docs/prd/
├── 00-产品概览.md              # 产品整体概述、术语定义、流程清单
├── [序号]-[流程名称].md        # 业务流程文档
├── [序号]-角色权限.md          # 角色定义和权限矩阵
└── [序号]-附录.md              # 接口清单、数据字典、错误码
```

### 文档编号规则
- `00-`：产品概览（必须，固定）
- `01-99`：业务流程（根据实际模块数量灵活分配）
    - 建议核心流程用 `01-09`
    - 支撑/辅助流程可继续编号
- `[序号]-`：角色权限（必须，固定）
- `[序号]-`：附录（必须，固定）

### 命名格式
| 文档类型 | 命名格式 | 示例 |
|---------|---------|------|
| 产品概览 | `00-产品概览.md` | 00-产品概览.md |
| 核心业务 | `[序号]-[流程名].md` | 01-物料开发流程.md |
| 角色权限 | `[序号]-角色权限.md` | 10-角色权限.md |
| 附录 | `[序号]-附录.md` | 11-附录.md |

## 内容规范与要求

### 1. 表格优先
属性定义、规则说明、接口清单使用Markdown表格

### 2. ASCII图表
流程图、架构图、关系图使用文本图形

### 3. 术语一致
全文使用一致的术语，在术语定义章节明确定义

### 4. 技术栈标注要求（重要）

#### Rosefinch技术组件标注
- **必须检查**：扫描 `references` 目录，识别所有以 `rosefinch` 开头的依赖引用
- **重点标注**：在所有更新的PRD文档中，将rosefinch相关技术以**加粗**或【重点】标记突出显示
- **标注位置**：
  - `00-产品概览.md` 的技术架构章节
  - 各业务流程文档的"使用到的技术列表"中
  - 角色权限文档中的权限组件
  - 附录文档中的组件清单

#### 禁止事项
- **禁止虚构服务类**：只能引用代码中实际导入的Rosefinch类
  - 允许：`com.catl.rosefinch.core.common.base.Results`
  - 禁止：虚构 `RosefinchWorkflowService`、`RosefinchFileService` 等不存在的服务类
  - 禁止：虚构 `@RosefinchPermission` 等不存在的注解
- **验证方法**：必须检查代码中实际的import语句，确认类确实存在

#### 真实表名要求（重要）
- **禁止推断/虚构表名**：不要使用 `apqp_` 前缀推断表名
- **必须从 `@TableName` 注解提取**：扫描所有实体类文件，记录真实的 `@TableName` 值
- **示例**：看到 `@TableName("process_instance")` 就用 `process_instance`，不要用 `apqp_process_instance`

## 刷新操作步骤

### 步骤1：变更识别
```bash
# 扫描代码库中的变更
git diff HEAD~1 HEAD
# 或者分析特定文件的变更
```

### 步骤2：影响分析
- 分析变更代码文件的功能模块
- 识别受影响的业务流程
- 确定需要更新的文档位置

### 步骤3：文档更新
- 更新相应的流程文档（如01-XX流程.md）
- 调整接口清单（如附录.md中的接口部分）
- 修订数据字典和错误码
- 更新角色权限定义（如10-角色权限.md）

### 步骤4：版本管理
- 为更新文档添加版本号（如v1.1、v2.0）
- 记录更新日志和变更说明
- 更新文档的最后更新时间

### 步骤5：验证输出
- 验证文档内容准确性
- 确保与代码实现一致
- 生成更新后的PRD文档
- **执行质量检查清单**（见下文）

### 步骤6：质量检查（必须执行）

#### 6.1 文档数量校验
- [ ] 是否更新了对应编号的业务流程文档？
- [ ] 文档编号是否保持连续性？

#### 6.2 内容完整性校验
- [ ] 所有术语都有定义
- [ ] 流程步骤编号连续
- [ ] 状态流转完整（无死状态）
- [ ] 角色权限覆盖所有功能
- [ ] 接口清单与代码一致
- [ ] 数据字典完整
- [ ] 错误码定义齐全
- [ ] 文档间引用正确

#### 6.3 真实性校验（重点）
- [ ] **表名使用真实@TableName值**
  - [ ] 检查了所有变更实体类的`@TableName`注解
  - [ ] PRD中使用的表名与代码中的`@TableName`值完全一致
  - [ ] 没有使用推断/虚构的表名
- [ ] **Rosefinch组件已识别并重点标注**
  - [ ] 扫描了`references`目录下的rosefinch依赖
  - [ ] 在各业务流程文档中正确标注rosefinch组件
  - [ ] 没有虚构Rosefinch服务类或注解

#### 6.4 缺失内容处理
如果发现任何缺失：
- 立即标记缺失项：在对应位置标注 【待补充：原因】
- 记录缺失原因：在文档末尾添加"待补充事项"表格
- 向用户报告：明确告知哪些内容无法从代码变更中推导，需要人工补充

## 注意事项

### 1. 变更范围确认
- 确保准确识别变更的影响范围
- 分析Git Diff时不要遗漏关联文件的变更
- 评估变更对上下游流程的影响

### 2. 内容准确性
- 更新内容必须与代码实现完全一致
- 不要推测未在代码中体现的业务逻辑
- 对于不确定的内容标注"待确认"

### 3. 版本控制
- 为每次更新维护正确的版本信息
- 版本号遵循语义化版本规范（v1.1、v2.0等）
- 保留完整的更新历史记录

### 4. 文档一致性
- 保持文档格式和术语的一致性
- 确保多个文档间的引用关系正确
- 更新一处时检查是否需要同步更新其他文档

### 5. 可追溯性
- 保留变更记录，便于后续追溯
- 记录变更来源（Git Commit Hash）
- 说明变更的业务原因

### 6. 真实性约束（重要）
- **表名真实性**：必须从 `@TableName` 注解提取，禁止推断/虚构
- **Rosefinch组件真实性**：必须检查实际import语句，禁止虚构服务类或注解
- **接口真实性**：必须基于实际代码中的Controller/路由定义
- **字段真实性**：必须基于实际实体类字段

### 7. 技术栈标注规范
- 所有Rosefinch组件必须以**加粗**或【重点】标记
- 在 `00-产品概览.md` 中必须单独列出Rosefinch技术组件小节
- 各业务流程文档的"使用到的技术列表"中优先列出rosefinch组件
- 在附录文档中列出rosefinch组件完整清单

### 8. 完整性要求
- 每次更新必须包含完整的变更说明
- 数据模型变更必须同步更新数据字典
- 接口变更必须同步更新接口清单
- 权限变更必须同步更新角色权限矩阵

## 最佳实践

### 1. 定期同步
- 建议在每次代码提交后同步更新PRD
- 每月进行一次全面的PRD文档审核
- **每次更新必须执行质量检查清单**

### 2. 变更管理
- 建立变更审批流程
- 保留变更历史记录
- 重要变更需经过评审
- **确保变更内容与代码实现完全一致**

### 3. 质量保障
- 更新后进行内容验证
- 确保与代码实现完全一致
- 保持文档的可读性和完整性
- **严格执行真实性检查（表名、Rosefinch组件）**

### 4. 保持客观

### 5. 标注不确定性
无法从代码变更明确推导的需求，标注"待确认"

### 6. 使用专业术语
使用行业通用的产品/技术术语，避免口语化

### 7. 结构清晰
使用标题层级、列表、表格提高可读性

### 8. 迭代完善
