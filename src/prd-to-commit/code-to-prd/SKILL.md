# Code to PRD - 代码转产品需求文档

此技能帮助你将现有代码库分析并转化为结构化的产品需求文档(PRD)，遵循企业级文档标准。

## 核心能力

1. **智能代码分析**：自动识别业务实体、流程、角色、权限
2. **标准文档生成**：生成符合企业规范的PRD文档、PRD中需要体现使用到的技术框架
3. **多维度覆盖**：功能需求、业务流程、数据模型、接口规范
4. **可追溯性**：从代码到需求的完整映射

## 输出文档结构

生成的PRD包含以下文档（存储在 `docs/prd/` 目录）：

```
docs/prd/
├── 00-产品概览.md              # 产品整体概述、术语定义、流程清单
├── [序号]-[流程名称].md        # 业务流程文档（核心、支撑、辅助流程）
├── [序号]-[流程名称].md        # 更多流程文档...
├── [序号]-角色权限.md              # 角色定义和权限矩阵（固定编号）
└── [序号]-附录.md                  # 接口清单、数据字典、错误码（固定编号）
```

**文档编号规则**：
- `00-`：产品概览（必须，固定）
- `01-99`：业务流程（根据实际模块数量灵活分配）
    - 建议核心流程用 `01-09`
    - 支撑/辅助流程可继续编号
- `[序号]-`：角色权限（必须，固定）
- `[序号]-`：附录（必须，固定）

**灵活拆分**：根据项目复杂度，可以：
- 简单的项目：2-3个流程文档
- 中等复杂度：5-8个流程文档
- 复杂系统：10+个流程文档，按模块拆分

## 工作流程

### 第一阶段：项目分析

#### 1.1 扫描项目结构
- 识别技术栈（package.json、pom.xml、go.mod等）
- 分析目录结构，理解模块划分
- 查找关键配置文件
- 识别入口文件和主模块

#### 1.2 分析代码结构
- **实体层**：识别核心业务实体（Model/Entity类）
- **接口层**：分析API端点（Controller/Handler）
- **业务层**：理解业务逻辑（Service）
- **数据层**：查看数据访问（Repository/DAO）
- **流程层**：识别关键业务流程

#### 1.3 提取业务信息
- 从代码中提取业务术语和领域名词
- 识别用户角色和权限控制
- 分析状态流转逻辑
- 提取业务规则和校验逻辑
- 识别数据关系和依赖
- **提取真实表名（重要）**：从实体类的`@TableName`注解中提取实际表名
  - 禁止推断/虚构表名（如`apqp_process_instance`、`user_project_relation`等）
  - 必须扫描所有实体类文件，记录真实的`@TableName`值
  - 示例：看到`@TableName("process_instance")`就用`process_instance`，不要用`apqp_process_instance`

#### 1.4 提取业务中使用的技术类型
**技术提取优先级**：
1. **优先检查**：扫描`references`目录，识别所有以`rosefinch`开头的依赖引用
2. **重点标注**：在**所有**生成的PRD文档中，将rosefinch相关技术以**加粗**或【重点】标记突出显示
3. **补充检查**：提取其他技术术语和技术名词

**Rosefinch组件使用规范（重要）**：
- **禁止虚构服务类**：只能引用代码中实际导入的Rosefinch类
  -  允许：`com.catl.rosefinch.core.common.base.Results`
  -  允许：`com.catl.rosefinch.core.oauth.SecurityContextHelper`
  -  允许：`com.catl.rosefinch.monitor.op.annotation.OperatorAudit`
  -  禁止：虚构 `RosefinchWorkflowService`、`RosefinchFileService` 等不存在的服务类
  -  禁止：虚构 `RosefinchPermission` 等不存在的注解
  - **验证方法**：必须检查代码中实际的import语句，确认类确实存在

**技术要求**：
- 识别项目中主要业务流程中使用到的技术
- 分析是否使用到"/references/**"中的模块，并将他补充到prd中
- **对于rosefinch技术栈**（必须在所有文档中标注）：
  - 在`00-产品概览.md`的技术栈章节单独列出"Rosefinch技术组件"小节
  - 在各业务流程文档的"使用到的技术列表"中优先列出rosefinch组件
  - 在角色权限文档中标注基于rosefinch的权限组件
  - 在附录文档中列出rosefinch相关接口规范
  - 标注rosefinch组件的版本号和用途

#### 1.5 文档长度评估
**超长文档识别标准**：
- Markdown行数超过 **200行**
- 字符数超过 **8000字符**
- 包含超过 **10个流程步骤** 或 **20个接口**

**超长文档处理策略**：
- **自动拆分**：按章节拆分为多个子文档（如：01-流程A-概述.md、01-流程A-详细步骤.md）

### 第二阶段：信息整理

| 维度 | 收集内容 | 来源 |
|------|---------|------|
| 产品定位 | 产品是什么、解决什么问题、目标用户 | README、配置、注释 |
| 功能模块 | 系统包含哪些功能模块 | 目录结构、Controller |
| 业务流程 | 关键业务流程和步骤 | Service层、状态机 |
| 数据模型 | 核心实体和关系 | Entity/Model类 |
| 用户角色 | 角色定义和权限 | 权限注解、角色常量 |
| 接口规范 | API列表和规格 | Controller/路由 |
| 非功能需求 | 性能、安全、部署 | 配置、中间件 |

**文档结构**：
```markdown

- 行业背景

- 系统定位

- 核心目标（表格：目标、说明、衡量指标）
- 业务价值

## 3. 术语定义
- 核心术语（表格：术语、英文、定义）
- 业务术语
- 技术术语

## 4. 业务范围
- 功能模块（ASCII架构图）
- 范围边界（包含/不包含）

## 5. 业务架构
- 整体架构（ASCII架构图）
- 流程关系图

## 6. 流程清单
- 业务流程清单（表格）
- 流程依赖关系图

## 7. 技术架构
- 整体技术栈（分类表格）
- **Rosefinch技术组件**（重点标注，单独小节）
  - 列出所有rosefinch依赖
  - 标注版本号
  - 说明在各模块中的用途

## 8. 角色清单(非必须)
- 角色定义（表格：名称、编码、职责、权限）

- 文档目录
```

```markdown
- 步骤属性表（名称、编号、角色、前置条件）
```

## 文档命名规范

PRD文档命名遵循以下规则：

| 文档类型 | 命名格式 | 示例 | 说明 |
|---------|---------|------|------|
| 产品概览 | `00-产品概览.md` | 00-产品概览.md | 固定编号00 |
| 核心业务 | `[序号]-[流程名].md` | 01-5M1E变更登记与审核主流程.md | 核心业务流程 |
| 支撑业务 | `[序号]-[流程名].md` | 04-数据导入流程.md | 支撑/辅助流程 |
| 角色权限 | `[序号]-角色权限.md` | [序号]-角色权限.md | 非必须 |
| 附录 | `[序号]-附录.md` | [序号]-附录.md | 非必须 |

**编号规则**：
- 00：产品概览（必须）
- 01-09：核心业务流程
- [序号]：角色权限（非必须）
- [序号]：附录（非必须）

可以根据实际需要灵活调整序号，只要保持合理的顺序即可。

## 第四阶段：导出文档（可选）

在生成所有文档后，必须执行以下校验：
#### 4.1 文档数量校验
- 是否生成了 00-产品概览.md？
- 是否至少生成了1个业务流程文档？
- 业务流程文档编号是否连续（01,02,03...）？
#### 4.2 内容完整性校验
对每个生成的文档执行以下检查：
##### 产品概览文档校验清单：
- 是否包含产品背景？
- 是否包含产品目标？
- 是否包含术语定义？
- 是否包含业务范围？
- 是否包含业务架构？
- 是否包含流程清单？
- 是否包含PRD文档清单？
##### 业务流程文档校验清单：
- 是否包含流程概述？
- 是否包含流程图？
- 是否包含流程步骤？
- 是否包含业务规则？
- 是否包含异常处理？
- 是否包含数据模型？
- 是否包含接口清单？
- 是否包含使用到的技术列表？
#### 4.3 缺失内容处理
如果发现任何缺失：
- 立即标记缺失项：在对应位置标注 【待补充：原因】
- 记录缺失原因：在文档末尾添加"待补充事项"表格
- 向用户报告：明确告知哪些内容无法从代码中推导，需要人工补充

#### 4.4 超长文档处理
当文档超过长度限制时（200行/8000字符）：

**处理流程**：
1. **检测**：在生成文档前计算预估长度
2. **执行**：超过限制时，自动按章节拆分为多个子文档

**拆分方案示例**：
- `01-物料开发流程.md`（超长）
  - 拆分为：`01-物料开发流程-概述.md` + `01-物料开发流程-详细步骤.md`

## 代码分析技巧

### 识别业务实体
- 查找 `class`、`interface`、`struct` 定义
- 关注数据库实体类（带@Entity、@Table、@TableName等注解）
- **提取真实表名**：从`@TableName`注解中读取实际的表名，禁止推断或虚构
- 分析DTO/VO类了解数据流转

### 识别业务流程
- 关注状态字段（status/state）的状态流转
- 查找审核/审批相关方法
- 分析Service层的方法调用链
- 识别定时任务和异步处理

### 识别用户角色
- 查找权限注解（@RequiresRoles、@PreAuthorize等）
- 分析用户类型常量或枚举
- 查看数据权限控制逻辑

### 识别接口规范
- 查找路由注解（@RequestMapping、@GetMapping等）
- 分析Controller/Handler类
- 查看API文档注解（@Api、@Operation等）

## 最佳实践

### 保持客观
基于代码实际实现描述，不过度推测未实现的功能

### 标注不确定性
无法从代码明确推断的需求，标注"待确认"

### 使用专业术语
使用行业通用的产品/技术术语，避免口语化

### 结构清晰
使用标题层级、列表、表格提高可读性

### 迭代完善
根据用户反馈持续完善PRD

### Word转换最佳实践
- **依赖安装**：确保已安装 `python-docx` 库
- **文件编码**：Markdown文件使用UTF-8编码
- **表格格式**：确保表格语法正确（|---|---|格式）
- **图片处理**：当前版本不支持图片转换，需要手动添加
- **复杂格式**：特殊的Markdown扩展语法可能无法完全转换

### 工作流程建议
1. 先生成所有Markdown文档
2. 用户确认内容后，再生成Word文档
3. Word文档用于演示和打印，Markdown用于版本控制
4. 定期同步更新Markdown和Word文档

## 执行步骤

### 详细执行流程

1. **探索代码库**: 使用文件读取工具探索项目结构和关键代码文件
2. **记录发现**: 将分析过程中的关键发现记录下来
3. **生成PRD**: 按照模板组织内容，在 `docs/prd/` 目录生成所有Markdown文档
    1. 必须完成上一阶段才能进入下一阶段
    2. 必须生成产品概览文档后才能生成其他文档
    3. **业务流程文档必须包含接口列表**：每个业务流程文档必须输出该模块下的所有接口列表（接口地址、方法、功能描述、权限要求）
    4. 必须完成完整性校验后才能输出文档
4. **询问接口详情补充（重要）**: 在所有模块文档生成完成后，必须询问用户
   - "是否需要为每个接口补充详细的接口文档（包含入参、出参、字段说明、示例等）？"
   - 如果用户需要，为每个接口生成详细的接口文档
5. **【重要】根据API生成接口流程图**: 在生成详细接口文档后，必须询问用户
   - "是否需要为每个API接口生成调用流程图（展示接口调用流程、数据处理流程、异常处理分支）？"
   - 如果用户需要，为每个API接口补充ASCII流程图，包括：
     - **接口调用流程图**：展示请求处理全流程
     - **数据处理流程图**：展示数据流转和转换
     - **异常处理流程图**：展示错误处理和分支
     - 流程图使用ASCII字符绘制，清晰展示处理步骤
     - 使用标准流程图符号：开始/结束、处理、判断、子流程
   - **【重要】API文档与流程图分离规范**：
     当生成API接口流程图时，必须遵循以下文档组织规范，确保文档清晰易读：
     
     #### 文档结构规范
     ```
     docs/prd/api/
     ├── README.md                    # API文档总览
     ├── API-01-流程模块.md            # API接口定义（简洁版）
     ├── API-02-质量门模块.md          # API接口定义（简洁版）
     └── flowcharts/                  # 📁 流程图专用文件夹
         ├── README.md                # 流程图索引
         ├── API-01-001-分页查询流程实例.md   # 详细流程图
         └── ...                      # 其他流程图文档
     ```
     
     #### 分离原则
     1.  **API文档保持简洁**：只包含接口基本信息、参数说明、请求/响应示例
     2.  **流程图独立成文**：详细的ASCII流程图放在 flowcharts/ 文件夹的独立 .md 文件中
     3.  **引用方式链接**：在API文档中使用简洁引用，而非嵌入大段流程图
     
     #### 引用格式规范
     在API文档的 `### 流程图` 章节中，使用以下格式引用：
     
     ```markdown
     ### 流程图
     
     📊 **详见**：[分页查询流程实例流程图](./flowcharts/API-01-001-分页查询流程实例.md)
     
     流程图包含：
     - 接口调用主流程
     - 数据权限过滤逻辑  
     - 分页查询处理流程
     - 异常处理分支
     ```
     
     #### 流程图文档内容要求
     每个流程图文档必须包含：
     - **接口信息**：接口地址、请求方法、所属模块
     - **主流程图**：使用ASCII字符绘制的完整流程图
     - **流程说明**：详细的步骤说明（1. 2. 3.）
     - **异常处理**：异常分支和错误处理流程
     - **业务规则**：数据校验规则和业务逻辑规则
     - **相关文档**：链接回API文档和业务PRD文档
     
     #### 哪些接口需要独立流程图
     - **核心业务流程接口**：创建、更新、审批、回退等关键操作
     - **复杂逻辑接口**：包含多步骤、条件判断、状态流转的接口
     - **批量操作接口**：批量审批、批量导入等需要展示批量处理逻辑的接口
     
     #### 示例：分页查询接口
     - API文档位置：`docs/prd/api/API-01-流程模块.md`
     - 流程图文档位置：`docs/prd/api/flowcharts/API-01-001-分页查询流程实例.md`
     - 引用方式：`📊 **详见**：[分页查询流程实例流程图](./flowcharts/API-01-001-分页查询流程实例.md)`

6. **生成Word（可选）**: 调用脚本将Markdown文档转换为Word格式
   ```bash
   python ~/.config/opencode/skills/code-to-prd/scripts/md_to_word.py ./docs/prd
   ```
7. **完成输出**: Markdown文档保存在项目中，Word文档输出到桌面
